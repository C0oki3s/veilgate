# Use case: Bug-bounty noise reduction

> **Summary:** Bug-bounty programs in 2026 receive a flood of submissions
> generated by autonomous AI agents — often with a fluent narrative
> attached but no actual vulnerability behind them. VeilGate tags traffic
> as agent-driven *before* it can produce a submission, giving triage a
> filter rather than a queue.

## The problem

A modern bug-bounty inbox is dominated by:

- Strix / HexStrike / CAI / PentestGPT scans that submit "findings"
  pulled from chained LLM hallucinations.
- Recon-only submissions ("you have `/admin` exposed!") generated by
  off-the-shelf scripts wrapped around an LLM summariser.
- Duplicate exploits chained automatically against any `?id=` parameter
  the agent finds.

Triage cost scales linearly with submission volume. The agents don't.

## The VeilGate setup

Run VeilGate in front of the bug-bounty-eligible scope. Use `challenge`
mode rather than `tarpit` — you want to filter, not punish, since
legitimate researchers also use automated tooling.

### `/etc/veilgate/veilgate.yaml`

```yaml
listen: ":8080"
upstream: "http://127.0.0.1:3000"
rules_dir: "~/.veilgate/rules"
mode: "challenge"

detector:
  score_tarpit_threshold: 90       # very rarely tarpit; bug bounty is delicate
  score_challenge_threshold: 35    # challenge most agent-shaped traffic
  window_seconds: 120

persist:
  enabled: true
  path: "/var/lib/veilgate/events.db"

metrics:
  listen: "127.0.0.1:9090"
```

### `~/.veilgate/rules/ml.yaml`

```yaml
enabled: true
score_max_points: 30
min_confidence_to_fire: 0.25       # slightly raised to suppress weak signal

path_redaction:
  enabled: true                    # always-on for shared bounty surfaces

miner:
  enabled: true
  auto_promote_confidence: 0.0     # never auto-promote on a public surface
```

The challenge mode serves a JavaScript proof-of-work that any real
browser solves transparently. Headless HTTP libraries — the bulk of
agent traffic — don't. Researchers using a real browser proceed; agents
get bounced.

## Metrics that prove it's working

Watch these in Prometheus:

- `veilgate_requests_total{decision="challenge"}` — the filter rate. A
  healthy bounty surface sits around 5–25 % depending on the scope.
- `veilgate_requests_total{decision="tarpit"}` — should be near zero.
  Anything above ~1 % means thresholds are too aggressive.
- `veilgate_signal_hits_total{signal="ml_agent_score"}` vs.
  `..{signal="suspicious_ua"}` — the ratio tells you whether the ML
  signal is doing real work or the rule-based scorer is carrying it.

Pair with submission-volume telemetry from your bounty platform. The
"valid finding rate" should rise; the absolute submission volume should
fall.

## Operational gotchas

- **Never run `tarpit` mode on a bug-bounty surface without explicit
  scope language.** Researchers expect to interact with the real app.
  Tarpitting them is a trust-breaker.
- **Keep `auto_promote_confidence` at 0.** The miner will surface
  candidates that look agent-shaped but cover real researcher tooling
  (e.g. `httpx`-based recon). Promote by hand only.
- **Whitelist your own scanners and CI.** Add their egress IPs to
  `detector.trusted_ips`. Otherwise they'll fight your rules and burn
  through your budget reviewing internal noise.
- **Document the challenge in your scope.** Bounty researchers should
  know that automated scans hit a JS PoW. The fairness story is
  important.
